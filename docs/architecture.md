# Architecture

winotch is a [Tauri 2](https://v2.tauri.app) app: a Rust process that owns everything with side effects, and one transparent, always-on-top WebView2 window that draws the island in TypeScript. A second small Rust binary, `winotch-hook`, is what Claude Code runs. This guide describes the pieces, the rules that hold them together and where to find each one.

## The pieces

**`winotch-hook`** (`hook/`) is a relay with no dependencies but `serde_json`. Claude Code runs it on every hook event. It reads the event on stdin, adds a little terminal context, and hands it to the app over a named pipe named after your account's SID, after checking the server process is yours. It never blocks Claude Code: every step runs under a deadline, and without an answer it prints "no opinion" and exits. Only a permission request waits, up to 110 seconds. Run as `winotch-hook mcp`, the same binary is the MCP server for Claude Code (`hook/src/mcp.rs`, its tools in `hook/src/mcp-tools.json`), a thin layer over the local API. The app copies the relay to `%LOCALAPPDATA%\winotch\bin\` at every start, so the hooks and the MCP command always point at one stable path.

**The app** (`src-tauri/`) owns state and side effects:

- the pipe server and the hook events (`pipe.rs`), the install of hooks and the status line relay with a diff and a backup (`hooks.rs`, `config_file.rs`), and adding the MCP server through `claude mcp add` (`claude_code.rs`);
- Claude Code's sessions on disk and the chat that runs `claude -p` or types into an open terminal (`sessions.rs`);
- the app registry and the local API (`apps.rs`), and the built-in apps: GitHub (`github*.rs`), Gmail (`mail/`), Spotify (`spotify.rs`), Notion and Stripe (`integrations.rs`), Today (`today.rs`);
- voice: local speech recognition (`speech/`), dictation (`flow/`), the Notetaker (`notes/`) and « OK Tent » (`voice/`), with the Claude API for what needs it (`claude.rs`);
- the island's window and the pointer (`island.rs`), the tray (`tray.rs`), global shortcuts (`shortcuts.rs`), secrets in Credential Manager (`secrets.rs`), settings (`settings.rs`), and what differs per platform (`platform/`).

**The island** (`src/`) draws everything the user sees. It holds no secret and calls nothing on the network: it asks Rust through Tauri commands (`core/bridge.ts`) and listens to its events.

- `island/`: the window's shell, its sizes and motion (`island.ts`, `fsm.ts`), and the handlers for hook events, apps, shortcuts and voice.
- `views/`: each view of the open island: the overview, the approval and question cards, the chat, the bell, an app opened big, Today, the diff, Settings' host.
- `core/`: state and data with no DOM: `state.ts`, the pills, the apps snapshot, Today's quick-add parser, diffs, sounds.
- `mark/`: the island's character, the Tent mark, drawn in SVG with its liquid filter, and its launch greeting.
- `hub/`: the Settings pages, drawn inside the island.

## Two paths that never cross

- **Claude Code's sessions** come through the hooks and drive the island's own views: the live ticker and diffs, the approval and question cards, the finished and error cards, the badges, the mark's states. They never go into the feed.
- **The feed** (the bell) is for apps, and for what Claude posts on purpose through its tools, such as a draft waiting for your yes.

A waiting approval or question always wins: while one waits, no notification takes the island from it. And the island stays quiet while Claude works: a prompt or a tool call never opens it. It opens when a session finishes, fails or needs an answer.

## Apps: one registry

Every app is one entry of one registry in `apps.rs`, and every screen draws from its snapshot (the `apps` event): the pills, the bell's filters, Settings → Apps and the expanded view. Nothing on the front end decides which apps exist.

- An entry carries its id, name, kind (`builtin` or `api`), logo, pill, status, what is wrong or missing, whether it is shown and may open the island, and what its row in Settings needs (`none`, a key, Gmail's accounts, GitHub's sign-in).
- The built-ins (`BUILTINS`) are always registered, set up or not. Their modules write into the registry through an internal API (`set_internal_items`, `post_internal`, `set_problem`, `set_available`, `set_internal_handler`).
- An outside app calls `POST /v1/apps` and is in the next snapshot. A new built-in is one `Builtin` entry, its logo in `scripts/gen-logos.mjs`, and a module that writes through the internal API; a card of its own is optional (a presenter in `core/app-detail.ts`).
- On/off and quiet belong to the user, for every app alike (`apps.json`). A built-in that is off is not polled.

## The island's window

There is one window. The island grows and shrinks inside it, and everything outside the island's shape lets the pointer through. Settings and dictation live inside it too, so a second WebView is never loaded.

Folded, the island is a line a few pixels high. Rust watches the pointer and wakes the page only near the island, or when the mark's eye would visibly move. The open island folds back to compact after 3, 5 or 10 seconds without the pointer, unless something holds it: a card waiting for an answer, the chat, a field with the keyboard, Settings.

## Staying light

Idle, winotch uses about 0 % CPU. The rules that keep it there:

- **Nothing draws while nothing changes.** Every animation loop stops when still; the few endless ones (a working session's breath, the music nod) run at 24 fps, not the screen's rate.
- **The pointer wakes nothing far away.** Rust sends the cursor only near the island or when the mark would move.
- **No endless CSS animation off screen**, and polls stop when their view is gone and skip unchanged data.
- **Never throttled.** WebView2 would treat the folded strip as hidden and throttle its timers, which made the dictation key late; the window's browser arguments turn that off, which costs nothing because the page idles by itself.

## Text and languages

Text is looked up by its English wording, `t("Allow")`, in ten languages. `src/i18n/strings.json` holds the strings that came from Coucou's catalog and `src/i18n/extra.json` the ones written for winotch; Rust reads the same two files (`src-tauri/src/i18n.rs`) for the tray, notifications and errors. A test fails when a string the code shows is missing a language, or when a known English string is left outside `t()`.

## Tests and previews

- `npm test` runs the island's logic (state, pills, the hook handling, diffs, the quick-add parser, i18n…) under Node with a small fake DOM, and the MCP server end to end: `winotch-hook mcp` against a stand-in for the API.
- `cargo test --workspace` runs the Rust tests: the registry and the API's limits, settings migration, hook payloads, Gmail parsing, Today, shortcuts and more.
- `dev/*.html` show one view in a real island on sample data, in a plain browser: `npx vite`, then for example `/dev/session-preview.html?state=approval`, `/dev/appdetail-preview.html`, `/dev/today-preview.html?view=calendar` or `/dev/settings-preview.html?page=welcome`.
